In a Meta E5 Interview you're asked to “Design Leetcode.”

As a senior/principal level engineer, I would follow the following playbook to show my depth:

The Playbook:
[1] Requirements: Safety First

- Don't just list features; frame the constraints.
- The Trap: Treating this like a standard CRUD app.
- The Reality: We are executing hostile user code.
- Security and Isolation are P0.
- The Scale: 100k concurrent users during a contest. We need Availability over Strict Consistency (a 3-second stale leaderboard is fine).

[2] API Design: The Async Pattern

- Avoid holding HTTP connections open while code runs.
The Flow:
- POST /submit -> Returns 201 Created + submissionId immediately.
- GET /submissions/{id} -> Client polls this every 2s for the verdict.
- Why: This keeps the API tier fast and stateless. If a solution takes 5s to run, we don't want the web server thread blocked.

[3] High-Level Storage
- Start simple, but split the heavy lifting.
- SQL (Postgres): Use this for Users, Submissions, and metadata. We need ACID guarantees for contest timing and submission history.

- Object Store (S3): Store large problem descriptions, test cases, and images here.
- The Win: Keeping heavy blobs out of Postgres keeps the primary DB cache-friendly and fast.

[4] The Core Challenge: Code Execution
- This is the most critical part of the interview.
- The Rule: Never run user code on the API server.

- The Architecture: Use a dedicated Code Runner Cluster.
Isolation Strategy:
- Sandboxing: Every run executes in an ephemeral Docker container.
- Lockdown: Read-only filesystem, No outbound network (prevent internal scanning), and strict CPU/RAM limits.
- Timeouts: Hard kill after 5 seconds to prevent infinite loops.

[5] The Leaderboard: Redis Sorted Sets
- Calculating ranks via SQL GROUP BY is too slow for real-time contests.
- The Solution: Redis Sorted Sets (ZSET).
- Key: leaderboard:{contestId}
- Scoring: Score = SolvedCount + (1 / TimeTaken). This ranks primarily by problems solved, with time as the tie-breaker.
- Performance: Updates (ZADD) and Reads (ZRANGE) are O(log N). This handles 100k users easily.

[6] Handling Contest Spikes
- Traffic isn't flat; it spikes right before the contest ends.
- The Bottleneck: If the API talks directly to the Runner Cluster, the Runners will overload and drop requests.
- The Fix: Insert a Message Queue (Kafka/SQS) between the API and the Runners.
- Why: The queue acts as a buffer. If 10,000 people submit at once, the API accepts them all instantly, and the workers process the backlog as fast as they can without crashing.

Summary:
You pass this interview by proving you can handle the trade-offs, for example, SQL for data integrity, Redis for speed, Containers for safety, and Queues for resilience.

After you've spent years doing backend engineering, you realise that everything is a wrapper:

- an API endpoint is a wrapper over a controller
- a controller is a wrapper over business logic
- a business logic is a wrapper over a service class
- a service class is a wrapper over repositories
- repositories are a wrapper over ORM calls
- ORM is a wrapper over SQL queries
- SQL queries are a wrapper over indexes and execution plans
- an execution plan is a wrapper over a database’s internal engine

- AND that engine is a wrapper over one simple truth:

a system is only as fast as the slowest part of your design
(A simple analogy I love: the happiest mood of a parent is the saddest mood of their child)

1 one piece of advice I would give to my 24-year-old self interviewing for backend roles:

Never fall into the trap of trying to learn everything.
Because you simply cannot.

This is NOT a System Design interview:

Kubernetes
Kafka
gRPC
Redis
Postgres
SQS
API Gateway
Docker
Consul
Envoy
Prometheus

Yes, these are important tools that are quite popular, but…

Interviewers don’t care how many tools you can list.
I wouldn’t as an interviewer as well.

They care how deeply you understand the fundamentals that drive systems.

If you’re interviewing for a backend or system design role, 80% of the discussion will be around:

→ How to scale reads and writes
→ How to store data
→ How your components talk to each other
→ How to handle failures

(𝘠𝘦𝘴, 𝘪𝘯 𝘵𝘩𝘢𝘵 𝘦𝘹𝘢𝘤𝘵 𝘴𝘦𝘲𝘶𝘦𝘯𝘤𝘦.)

Sure, Kafka, Redis, or Kubernetes might show up…
But only as tools to support the fundamentals.

The real questions are always the same:

– Can you design a system that doesn’t fall over under load?
– Can you reason about trade-offs?
– Can you explain why you’d choose A instead of B not just list both?

This is what senior engineers are evaluated on:

• Understanding latency vs throughput
• Knowing when to cache and when not to
• Knowing how to keep a system alive when something fails
• Knowing the difference between “what works” and “what scales”

Not how many logos you can memorize.

And here’s something most candidates don’t realize:
If you get a question you don’t know, you can still pass.

Just do this:

• Explain how you’d approach learning it
• Mention similar tools you picked up quickly
• Walk through your reasoning, even if you don’t know the exact syntax

Interviewers don’t expect you to know every tool.
They expect you to think like an engineer.

So stop trying to master 10 technologies at the same time.

Go deep into the 3–4 skills that actually get you hired:

• Data modeling
• Storage + caching
• Communication patterns
• Scaling fundamentals

Master these, and any tool becomes easy.

Recently in an interview a candidate was asked regarding the four core functional interfaces of Java 8. He went blank when asked what each of them is about.

Here are the 4 core functional interfaces:
1. Predicate<T>
Tests if an input satisfies a condition, returning true or false.
How I remember: Like a bouncer at a club checking if you're on the guest list before letting you in.

2. Function<T, R>
Takes one input and produces one output, transforming data.
How I remember: A vending machine that accepts coins (input) and dispenses a soda (output).

3. Supplier<T>
Provides a result without needing any input, like a factory method.
How I remember: A magic hat that pulls out a rabbit on demand, no tricks required upfront.

4. Consumer<T>
Accepts an input and performs an action on it, but returns nothing.
How I remember: A trash can that takes your garbage (input) and just disposes of it, no receipt given
