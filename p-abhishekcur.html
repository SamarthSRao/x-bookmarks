One thing I've started to notice the longer I study, it's superb.

whether it's physics, math, systems engineering, ML, or AI inference, the same patterns keep showing up. different names, different notation but underneath, it's usually the same few ideas wearing new clothes.

you end up asking the same questions every time:

- Where's the bottleneck?
- What's the trade-off?
- What are the real constraints?
- Can this run in parallel?
- Where is time or memory being wasted?
- What's the simplest version that still works?

The domain changes. the vocabulary changes. but the way you think stays surprisingly the same.

That's why the start of anything feels so overwhelming. everything looks new, and it's easy to assume everyone else is just smarter than you.

Then one day it clicks. you realize you were never learning thousands of unrelated things, you were just seeing the same patterns show up in different places.

So the hard part was never "learn more." It's staying with the craft long enough, through the boring and confusing parts, until those patterns stop being things you look up and start being things you just see.

Here's some example:
The memory-vs-compute trade-off.

Say you're computing Fibonacci numbers. The naive recursive version recalculates the same values over and over, fib(50) takes billions of calls and crawls.

So you store each result the first time you compute it, and just look it up afterward. Suddenly it's instant. You spent a little memory to save a huge amount of time.

That exact trade-off shows up everywhere once you notice it:

- Caching a slow database query so you don't hit the database twice.
- Dynamic programming filling a table so each subproblem is solved once.
- A GPU keeping activations in fast memory instead of recomputing them during training.

Different fields, different vocabulary: memoization, caching, DP, activation storage, but it's all the same idea: spend memory to save time.

That's the pattern. Once you've seen it in one place, you start recognizing it in all the others.

If you're early in something and it feels like too much, that's not a sign you're behind. keep going. give it good time.

Every iteration, you return sharper. Every rejection, you return with less to fix. Until one day, there's almost nothing left to fix.
The people who look "overnight successful" from the outside? They just failed faster, extracted harder, and showed up again when everyone else sat out.

Stop mourning your failures. Mine them.

Something clicked for me today about how we choose tech...
So I've been thinking about this a lot lately, and wanted to share what I learned.
Being dogmatic and being pragmatic, both actually matters.
I know, sounds contradictory right? But hear me out.
Being Dogmatic (Having Standards)
This is about having non-negotiable principles you stick to:
-Code quality standards you won't compromise on
-Security practices you always follow
-Testing requirements that must be met
-Architecture patterns that ensure maintainability

For example: "We ALWAYS sanitize user input" or "Our APIs MUST be documented"

Being Pragmatic (Being Flexible)
But then there's the practical side, adapting to what actually works:
-Choosing tools that solve YOUR specific problem
-Shipping working code over waiting for perfect code
-Using "boring" tech if it's proven and reliable
-Not reinventing the wheel just because you can

Real example: "We don’t need microservices for this project. A single well-structured monolith is faster to build, quicker to deploy, and easier to debug. why overcomplicate it?"

Where I think the balance is
The insight that hit me: You actually need BOTH at the same time.
-Be dogmatic about principles (security, performance, user experience)
-Be pragmatic about tools (frameworks, languages, libraries etc.)

Like, I've seen devs say "I only code in Rust because it's the best", that's being dogmatic about tools, which feels limiting, it's not a good thing in the run.

But saying "I choose the right tool for each job, but I never skip code reviews", that's being pragmatic about tools while staying dogmatic about quality.

What I'm taking away from this
Have strong values, but don't be religious about technology choices.

The framework/language is just a tool. What matters is: does it solve the problem?
Does it serve your users?
Does it help you ship?

And honestly (In mine's view)
I think I must be like water, rigid when needed, flexible enough to take any shape when the situation demands it.

What do you think?
Am I missing something?
Drop your thoughts, I genuinely love learning from your feedback and digging deeper for real facts.

In summary:
"Being rigid and flexible matters, but based on context, not bias."

This is how rustc compiler works:

Source Code (.rs files)
↓
Lexical Analysis (Lexer/Scanner)
↓
Parsing → Abstract Syntax Tree (AST)
↓
Macro Expansion
↓
Name Resolution & Item Collection
↓
Lowering AST → HIR (High-level IR)
↓
Type Checking & Borrow Checking (on HIR)
↓
Constant Evaluation (const eval)
↓
Lowering HIR → MIR (Mid-level IR)
↓
MIR Optimizations & Analysis
↓
Code Generation Preparation (MIR → LLVM IR)
↓
LLVM Optimization Passes
↓
Machine Code Generation
↓
Linking → Executable / Library
