We just fought a nasty Kafka bug in production and it all came down to consumer lag + silent connection drops.

Here’s what happened, what we learned, and what you should absolutely check in your own systems.

The Incident

We had a Kafka consumer that normally processes messages in microbursts.

Some partitions often sit idle for long stretches - minutes at a time because upstream traffic is uneven.

Everything was working fine… until suddenly it wasn’t.

Out of nowhere, one of the consumers started falling behind.
Lag kept increasing, even though traffic was low.
Logs showed nothing except a cryptic:

Connection reset by broker
Connection reset by peer
EOFException on FetchSessionHandler

And then… silence.

The process didn’t crash.
The consumer didn’t reconnect.
It just sat there alive-but-dead, holding a stale TCP connection and never issuing a new fetch request.

Classic zombie consumer.

The Root Cause

Kafka brokers drop idle connections after some timeout, especially when:

connections.max.idle.ms kicks in

The consumer hasn’t issued any fetch requests

The connection sits idle due to lack of traffic, long GC pauses, or slow processing

Network gear silently kills idle TCP sessions

When the broker finally closes the socket, the client sees a Connection reset.

But here’s the catch:

Your consumer may NOT automatically reconnect.

Depending on your client library and fetch loop implementation, you may accidentally:

- swallow the error

- exit the polling loop

- or keep retrying in a busy-wait without re-establishing a fresh connection

That’s exactly what happened to us.

The Fix: Explicit Reconnection Logic

We patched our consumer with a defensive pattern:

1. If the poll loop throws a transport-level exception (connection reset, EOF, broker disconnect):
→ immediately close the consumer and recreate a new one.

2. Add metrics around “time since last successful poll”
→ if this crosses a threshold, treat it as a stuck consumer and restart.

3. Add jittered backoff retries
→ to avoid hammering the broker during reconnection storms.

4. Ensure processing logic cannot block poll too long
→ delegate heavy logic to worker pools.

Now, instead of dying quietly, the consumer tears down its stale socket and becomes healthy again within seconds.

Some common Kafka Pitfalls That Bite Even Senior Teams

1. Low-traffic partitions are riskier than high-traffic ones

Idle partitions hit connection timeouts more often.

2. Kafka consumer loops must never block

If your processing takes 2 minutes, but max.poll.interval.ms is 1 minute → Kafka will kick you out.

3. Treat all I/O exceptions as signals to rebuild the consumer

Kafka clients aren’t always robust against partially-dead TCP sessions.

4. Monitor consumer-liveness, not just consumer-lag

Lag only increases when messages exist.
Stuck consumers on empty partitions show zero lag — and still be dead.

5. Networking gear can kill idle TCP connections silently

Load balancers, firewalls, NAT devices — any of them can drop your connection after X minutes of inactivity.

Patterns Every Kafka Team Should Implement

- Recreate consumers aggressively on network errors

- Health metrics: last poll time, last commit time

- Graceful backoffs with jitter to avoid herd effects

- Dedicated thread for the poll loop only

- Async processing (no blocking inside poll)

- Use session.timeout.ms and max.poll.interval.ms tuned realistically

- Watch for rebalance storms when consumers restart too often

Many Kafka outages don’t come from message volume they come from assumptions that “the client will reconnect automatically.”

In reality, a single half-dead connection can hold your entire pipeline hostage.

We learned this the hard way, but the fix now makes our system significantly more resilient.

If you run Kafka in production, don’t wait for a 3am pager.
Add reconnection logic and liveness metrics today.

In college, I always struggled with ACID properties in DBMS.
I knew the full form.
Atomicity, Consistency, Isolation, Durability.
But honestly, none of it made sense to me back then.

I only understood it properly years later, while working on real systems at Cisco.
Let me explain it the way I finally understood it.

Imagine you have a savings account with 25,000 in it.
Your bank needs you to maintain a minimum balance of 5,000.
And you are transferring some amount to a friend.

A transfer has two steps.
Money goes out of your account.
Money goes into your friend’s account.

If the first happens and the second fails,
you end up losing money
and your friend still doesn’t receive anything.
That is an inconsistent and unfair state for the system.

Atomicity simply means
both steps must succeed together
or none of them should happen.

Consistency means
your transfer should not break the rules of the system.
If you try to send your full 25,000
your balance becomes zero
which violates the minimum 5,000 requirement.
So the system should not allow it.

Isolation is about timing.
Your account gets debited at one moment.
Your friend gets credited a little later.
If someone checks the balances in between,
they should not see half-done data.
They should either see the situation before the transfer
or after the transfer,
but never the messy middle.

Durability is the simple idea
that once the money has been transferred and committed,
it should never be lost
even if there is a crash or power failure.

That’s ACID.
The real version.
The version that finally clicked for me.

If you want me to simplify more concepts like this,
tell me which one I should take up next.

If you need to cache a query result in Postgres, consider using a materialized view before introducing another caching solution. Let’s take a simple example.

Imagine we define a regular view that returns all orders for the last day (24 hours):

CREATE VIEW sales_summary AS
SELECT id, product_id, purchased_at
FROM orders
WHERE purchased_at >= now() - INTERVAL '1 day';

A view in Postgres is just a named query that you can call like this:

SELECT count(*) FROM sales_summary;

Every time you call the view, Postgres runs the underlying query and returns the latest data.

But what if you want the view to cache its result and refresh it only once an hour? Easy. Add the MATERIALIZED keyword when creating it:

CREATE MATERIALIZED VIEW sales_summary AS
SELECT ...

During the first invocation, the materialized view stores (caches) its result, which is returned on subsequent calls. Even if new orders are added to the table, the view will ignore them until you refresh it explicitly:

REFRESH MATERIALIZED VIEW sales_summary;

It’s up to you how and when to refresh the view. You can do this hourly or more/less frequently. You can call the REFRESH statement from your app logic or use the pg_cron extension. Postgres gives you plenty of options.

Learn more in Chapter 2 of the Just Use Postgres book: manning.com/books/just-use-postgres

When I started learning Kubernetes, this confused me:

Why do I need annotations if labels can do the same thing?

Both are key-value pairs. Both sit in metadata. Why not just use labels for everything?

Labels = identification
Kubernetes indexes them. Controllers use them to find and group objects. Services use them to route traffic. ReplicaSets use them to manage pods.

"kubectl get pods -l app=frontend" runs fast because labels are indexed.

Annotations = context
Not indexed. Not used for selection. Just metadata, build timestamps, Git commits, owner info, monitoring configs.

Kubernetes ignores them. External tools might care. But the cluster? Doesn't touch them.

The one-line rule:
If Kubernetes needs to select it → label
If humans/tools need to read it → annotation

Did you know this before?

JSON is great… but Protobuf is 🔥

We learned this the hard way.

Had a Go backend with 15+ microservices. Everything talked JSON. Worked fine at first. Then traffic scaled, and things were not as good now. Here is our story...

---

The problem:

> marshalling and unmarshalling JSON was eating CPU. every request, every response, every service hop - parsing strings into structs, structs back into strings.

> payloads were bloated. field names repeated in every single object. a list of 1000 items meant 1000 copies of "user_id", "created_at", "transaction_type".

> no schema enforcement. services would drift. someone adds a field, someone else typos a key, downstream breaks silently. debugging was archaeology.

---

We went ahead with the migration:

> defined `.proto` files as the source of truth. shared them across repos. generated Go code with `protoc-gen-go`.

> swapped `encoding/json` for `proto.Marshal` and `proto.Unmarshal`. mostly mechanical. the compiler caught type mismatches instantly.

> switched inter-service calls to gRPC. HTTP/2, streaming, built-in deadlines. felt like upgrading from bicycle to bullet train.

---

The results were mind boggling:

> payload sizes dropped 40–60%. binary encoding, no field names, varint integers. less bytes over the wire, faster network hops.

> CPU usage on serialization dropped ~30%. Go's protobuf library is tight. no reflection, no runtime parsing.

> p99 latency between services fell by 25%. not magic - just less work per request compounding across hops.

> schema mismatches became compile errors. no more "why is this field null in prod" at 2am.

But there are some tradeoffs too:

> debugging is harder. can't just `curl` and read the response. need tooling to decode.

> `.proto` management adds overhead. versioning matters. breaking changes need coordination.

Worth it though. JSON for external APIs. Protobuf for everything internal.

Kafka's "Zero-Copy" & Caching Magic

Kafka's efficiency comes from stepping aside and letting the Linux kernel handle data movement and caching directly.

1. Zero-Copy Data Transfer (sendfile())
Kafka uses the sendfile() system call to transfer data from disk to the network socket. This bypasses the application's userspace entirely, avoiding unnecessary data copying and CPU cycles. Data flows from the disk, through the kernel's page cache, and directly to the network interface card (NIC) buffer.

2. Memory-Mapped Files & Page Cache (mmap())
Kafka uses mmap() to map its index files directly into memory. This allows it to access file data as if it were in memory, with the OS managing loading and eviction. Both reads and writes go through the Linux page cache, leveraging decades of kernel optimization for caching without Kafka having to build its own layer.

Go's runtime is designed to efficiently manage thousands of concurrent operations by building on top of powerful Linux primitives.

3. Event-Driven Concurrency (epoll)
The Go netpoller uses epoll to manage network I/O. Instead of blocking a thread for each connection, a single event loop monitors many sockets. Goroutines are "parked" (suspended) until their socket is ready for I/O, at which point they are "unparked" and resumed. This allows for massive concurrency without the overhead of many OS threads.

4. Low-Level System Interaction (futex, madvise)
Go's high-level constructs map directly to efficient low-level syscalls. For example, Go's mutexes and other synchronization primitives are built on top of futex (fast userspace mutex) for efficient locking. The garbage collector uses madvise to hint to the kernel about unused memory pages, allowing the OS to reclaim them.

The syntax may be high-level, but the machinery underneath is pure Linux.

Languages and frameworks change, but these fundamental syscalls remain the bedrock of high-performance systems.

RabbitMQ vs Kafka: Which One and When?

Both handle messaging, but their architectures solve different problems.​

RabbitMQ: Traditional Message Broker
- Push model: broker pushes messages to consumers​
- Complex broker, simple consumer​
- Throughput: 4K–10K messages/sec​
- Messages deleted after acknowledgment​
- Flexible routing via exchanges (direct, topic, fanout)​
- Multiple protocols: AMQP, STOMP, MQTT​

Kafka: Event Streaming Platform
- Pull model: consumers poll for messages​
- Simple broker, complex consumer​
- Throughput: 1M+ messages/sec​
- Messages retained for configurable period (replay anytime)​
- Partition-based ordering guarantees​
- Exactly-once semantics​

Use RabbitMQ when you need flexible routing patterns, priority queues, and the broker should handle delivery complexity.

Use Kafka when you need high-throughput event streaming, event replay capabilities, and strong ordering guarantees for data pipelines.

Love this problem, had to deal with similar thing for merging multiple market data feeds + app logs in Go.

Your semaphore idea is basically:
“let every stream push ahead a bit, but not too far”
which is exactly the right mental model.

There is a slightly simpler way though, if you’re ok with 1 in-flight item per stream:

Core idea:
for sorted streams, the globally smallest item is always among the current heads of each stream.
So you never really need more than 1 buffered element per input to decide the next output.

That means:

keep a min-heap of size ≤ N, one element per stream

only read from stream i when its previous element has already been popped from the heap

use Go’s “disable select case by setting channel to nil” trick instead of semaphores

Pseudo-architecture:

Have a coordinator goroutine:

tracks inHeap[i] bool for each input stream

tracks a min-heap of item{ value, streamIndex }

In a loop:

build a select over all input channels

for any i where inHeap[i] == true, set that channel to nil so select will never read from it

when select receives from ch[i]:

push (value, i) into the heap

set inHeap[i] = true

in the same loop, whenever the heap is non-empty:

pop the minimum item

send it to out

set inHeap[item.streamIndex] = false (now we’re allowed to read the next element from that stream)

Backpressure here is “free”:

producer writing to ch[i] will block if:

its previous item is still in the heap

and the consumer hasn’t popped it yet

we never let a single stream have >1 pending item in the heap

no extra semaphores, max memory ~O(N), and queue cannot be dominated by one fast input

Why this works well in practice:

sorted per-stream logs + 1 in-flight per stream is enough to always pick the global minimum

you avoid the “fast stream flooding” problem because that stream literally cannot progress until its head has been flushed to output

fairness comes from the heap: even if one channel is always ready, you still only ever keep one of its elements in play

Your approach (bounded semaphore, releasing on emit instead of receive) is basically a generalized version of this where maxBufferedPerChan > 1.
For pure chronological merge, the 1 item per stream version is often simpler to reason about and implement.

So if I had to summarise:

If you need strict merge of sorted logs → at most 1 pending item per stream + heap + nil-channel trick = simple and safe.

If you need more async slack per stream (burst tolerance etc.) → your bounded semaphore design is solid and more flexible.

Honestly, the hardest part here is not the heap, it’s understanding that “fairness” and “backpressure” can be done just by controlling how many in-flight items you allow per stream, not by trying to consume everything as fast as possible.

Here’s a real example of how ignoring idempotency can burn you - literally.

About 2 years ago, I was working at a startup where our payment flow relied heavily on idempotency keys (like most payment providers: Stripe, Razorpay, PayU, Cashfree, etc.).

The idea is simple, each payment attempt must have a unique, backend-generated idempotency key so that:

repeated retries don’t charge the user twice

- timeouts can be recovered safely

- webhooks can be reconciled deterministically

- follow-up queries about payment status use the same key

Well… we weren’t doing that.

The Flutter app was generating idempotency keys on the client side, without reconciliation with our backend database.
And because of some retries + network issues + inconsistent key generation, the same payment was processed multiple times.

End result: we lost $10,000 in duplicate charges.
No fraud. No hack. Just poor idempotency.

Thankfully, I wasn’t fired mostly because I tracked the root cause quickly.
I remembered an odd flow where the app generated the id instead of the backend.
That tiny detail turned out to be the entire reason why our payment flow wasn’t deterministic.

Here’s the correct flow (for anyone who builds payments):

1. Backend generates the idempotency key

2. Backend sends this key to the client

3. Client passes the same key to the payment provider

4. Payment provider uses the key to dedupe retries

5. Webhook arrives → backend verifies using the same key

6. If payment seems “stuck”, backend queries the provider using the same key

7. No matter how many retries occur, only one payment is ever processed

This incident taught me that idempotency isn’t a “nice-to-have.”
It’s literally the difference between correct systems and catastrophic failures!!

◾ Each consumer fetches messages from its assigned partitions based on its committed offset.

◾ Kafka tracks committed offsets for each consumer in the group.

◾ Producers continue sending messages and consumers keep fetching and processing them based on their latest offsets.
◾ This cycle ensures ordered delivery and reliable consumption even with failures or restarts.

👉 Kafka offers mechanisms for handling failures and ensuring at-least-once or exactly-once delivery semantics.

Docker isn’t truly native outside Linux, and here’s why

If you’re using Docker on Windows or macOS, your containers aren’t running directly on those operating systems. They run inside a small Linux virtual machine, created by Docker Desktop using technologies like WSL2, Hyper-V, or a hypervisor.

Docker was originally built only for Linux because containerization, at its core, depends on Linux kernel features, specifically namespaces and cgroups.

- Namespaces handle isolation, giving each container its own sandboxed view of system resources like processes, networks, mount points, and filesystems.

- Cgroups manage and restrict resource usage (CPU, memory, bandwidth, I/O) so containers don’t overload the host.

Other operating systems simply don’t implement these kernel mechanisms in the same way, which is why Docker can’t run Linux containers directly on Windows or macOS kernels. The workaround? Docker runs a lightweight Linux VM behind the scenes, and everything operates inside, sharing its kernel, not the actual host OS kernel.

Yes, Windows containers exist and can run natively on the Windows kernel, but they are a separate container type. The moment you run a Linux container, a Linux kernel layer becomes mandatory, regardless of whether the host machine is running Windows or Mac.

A Kafka Partition is NOT a single file. It is a directory.

If a Partition was just one massive 10TB file, Kafka would be incredibly slow. Why? Because of Retention.

To enforce 'Delete data older than 7 days,' the OS would have to chop off the beginning of that 10TB file.

Filesystems hate this.

You can't easily 'delete the first 1GB' without rewriting the remaining 9TB.

The Solution =>

Segments & Rolling.

Kafka splits the partition log into smaller, manageable files called Segments.

Here is the physics of the Log:

1./ The 'Active' Segment at any given time, only one segment file is writable.

All new messages are appended here.

It stays in the OS Page Cache (RAM) because it is 'hot.'

This is why Kafka writes are fast, it’s just sequential RAM writes.

2./ The 'Roll' when the Active Segment hits a limit (default 1GB or 7 days), Kafka 'Rolls' it.

It closes the file.

It marks it as Read-Only.

It creates a new Active Segment.

3./ The Delete (Retention)
Kafka doesn't parse messages to delete them. It just looks at the file metadata. 'Is the newest message in 0000.log older than 7 days? Yes? Delete the whole file.'

Unlinking a file is an O(1) operation for the OS.

4./ The "Sparse Index" (how reads work)
If the data is split across 100 files, how does a consumer find Offset 5000? It doesn't scan 100 files.

Every .log file has a sibling .index file. This is a Sparse Index. It doesn't map every message. It maps every 4KB of data.

Offset 0 -> Byte 0

Offset 100 -> Byte 4096

Kafka does a binary search on the Index (which is small enough to fit in RAM), jumps to the nearest byte position in the Log, and scans the last few messages.

The Production Pitfall =>

Don't set your segment size too small. If you set segment. ms to 5 minutes on a low-volume topic, you will generate thousands of tiny files. You will hit the OS File Handle Limit (ulimit -n), and your Broker will crash because it ran out of 'open files.'

To summarise =>
Kafka isn't just 'writing to a log.'

It is managing a rolling window of immutable files to trick the OS into being a high-performance database.

Everyone knows B-Trees. Very few people actually know Bf-Trees and LSM Trees properly.

Quick 101 for context.

B-TREE
This is the classic index used by MySQL / Postgres.
Balanced tree, each node is a page on disk, keys kept sorted.
Reads are great: O(log N) lookups with a small number of page reads.
Writes are ok but not amazing – every insert/update eventually touches multiple pages and causes random I/O.
Disk page size and in-memory page size are basically the same mental model.

BF-TREE (a.k.a. Bε-tree style)
Bf-trees try to fix the write problem without throwing away the B-tree idea.
Key trick: decouple on-disk page size from in-memory cache entry size and add buffers to internal nodes.
Instead of pushing every insert down to the leaf immediately, you buffer a bunch of updates in upper nodes and flush them in batches.
Result:
– Fewer random writes (you turn many small writes into fewer big ones)
– Much better write throughput, especially for large indexes
– Still pretty good point/range read performance, but more logic to walk buffered updates

It’s like saying: “I want a tree only, but I want it to behave more like a write-optimized structure.”

LSM-TREE
Log-Structured Merge Trees go even more extreme on write optimization.
– All writes are first appended to a log (memtable) in memory
– Flushed to disk as sorted runs (SSTables)
– Background compaction merges these runs to keep things somewhat tidy
Reads:
– Need to check multiple levels / files (use Bloom filters, indexes to speed this up)
– Great for write-heavy workloads and SSDs
– This is what RocksDB / LevelDB / Cassandra style systems use

Very rough intuition:
– B-TREE: classic, great for mixed read/write, simple mental model
– BF-TREE: B-tree DNA + smarter buffering = better writes, still decent reads
– LSM-TREE: fully commit to log + merge world, amazing writes, more complex read/compaction behavior

“Bf-trees decouple on-disk page size from cache entry size”, 💯
It basically means:
we stopped treating “what’s on disk” and “what sits hot in memory” as the same structure, and that gives us more freedom to batch, buffer and optimize writes.

Even I am Curious when/if databases like MySQL/Postgres will ship a modern write-optimized index next to their classic B-trees. The hardware world has changed a lot, but most mainstream indexes are still stuck in 1980s design space.

Something clicked for me today about how we choose tech...
So I've been thinking about this a lot lately, and wanted to share what I learned.
Being dogmatic and being pragmatic, both actually matters.
I know, sounds contradictory right? But hear me out.
Being Dogmatic (Having Standards)
This is about having non-negotiable principles you stick to:
-Code quality standards you won't compromise on
-Security practices you always follow
-Testing requirements that must be met
-Architecture patterns that ensure maintainability

For example: "We ALWAYS sanitize user input" or "Our APIs MUST be documented"

Being Pragmatic (Being Flexible)
But then there's the practical side, adapting to what actually works:
-Choosing tools that solve YOUR specific problem
-Shipping working code over waiting for perfect code
-Using "boring" tech if it's proven and reliable
-Not reinventing the wheel just because you can

Real example: "We don’t need microservices for this project. A single well-structured monolith is faster to build, quicker to deploy, and easier to debug. why overcomplicate it?"

Where I think the balance is
The insight that hit me: You actually need BOTH at the same time.
-Be dogmatic about principles (security, performance, user experience)
-Be pragmatic about tools (frameworks, languages, libraries etc.)

Like, I've seen devs say "I only code in Rust because it's the best", that's being dogmatic about tools, which feels limiting, it's not a good thing in the run.

But saying "I choose the right tool for each job, but I never skip code reviews", that's being pragmatic about tools while staying dogmatic about quality.

What I'm taking away from this
Have strong values, but don't be religious about technology choices.

The framework/language is just a tool. What matters is: does it solve the problem?
Does it serve your users?
Does it help you ship?

I think I must be like water, rigid when needed, flexible enough to take any shape when the situation demands it.

Elasticsearch can easily handle 1TB / 16M rows.
The real problem is how you model + index it.

If I was starting from scratch, I’d do it like this:

1. First: clarify workload

Mostly reads? Mostly writes? Analytics or search?

Time based data (logs, events) or static records (users, products)?
Your index design totally depends on this, dont skip this step.

2. Do NOT dump all 1TB into a single index!!

Use time based indices if it is logs/events:

daily / weekly / monthly index like: logs-2025.11.17

This lets you: drop old data, move cold data to cheaper nodes, scale only hot data.

For static data, still split by logical boundaries (region / tenant / type) if needed.

3. Shard design (most noobs mess up here)

Too many shards will kill your cluster faster than too much data.

Target 30–50 GB per shard as a rough rule.

1TB data → around 20–30 primary shards total across all indices is usually fine.

Start simple: maybe 3–5 primary shards per major index, 1 replica.

Watch actual shard sizes and adjust for future indices, not for already created ones.

4. Mapping (this decides performance + storage)

Explicit mappings only, do NOT rely on dynamic mapping for everything.

Use:

keyword for exact matches / aggregations

text only for real full text search fields

Turn off things you don’t need: _source only if you really can, doc_values or fielddata only on fields you aggregate/sort on.

Avoid indexing large blobs / descriptions unless you really search them.

5. Hardware / cluster

Prefer SSD, spinning disks gonna hurt you badly at this scale.

Start with 3 data nodes (for HA) if you can:

16–32GB RAM per node

Heap around 50% of RAM but never more than ~30–31GB

Use dedicated master nodes in bigger setups, but for small cluster you can share.

6. Indexing strategy for that initial 1TB load

Use the Bulk API only.

Aim for 5–20 MB per bulk request, tune based on response times.

Multiple parallel bulk workers instead of one gigantic request.

While bulk loading:

Set index.refresh_interval = -1 (disable refresh)

Optionally set number_of_replicas = 0 during load

After load finishes: set replicas back to 1 and refresh_interval to 1s or whatever.

After big import, you can run a forcemerge to reduce segments, but only on read-mostly indices, not on hot write ones.

7. Query design

Use filters (bool + filter) for conditions on keyword / numeric / date fields, cause filters are cacheable and much cheaper.

Limit from/size deep pagination, use search_after / scroll for large scans.

Monitor slow logs to see bad queries.

8. Observability

Watch: heap usage, GC, search latency, index latency, queue sizes, shard counts.

If nodes are dying, first check shards and mappings before buying more hardware.

you can design a very solid layout.
But the high level answer:
1TB / 16M rows is not crazy for Elasticsearch
You just need: good mapping, sane shard count, bulk indexing, and time based indices instead of one giant “data” index.
