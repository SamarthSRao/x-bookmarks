MGManthan Gupta
@manthanguptaa · 18 Nov 2026

Notion took their whole product down for five minutes to split one database into 32.

They had run on a single Postgres database for five years while growing about 10,000x. Postgres gives every change a number, and it needs a cleanup process to keep that counter safe. That cleanup had started stalling. If the counter ever wrapped around, Postgres would stop accepting writes to protect old data. So they had to split up.

They wrote the splitting logic into their own app instead of using an off-the-shelf tool, because they wanted to control where each row ended up.

That control mattered because a change can only be all-or-nothing inside one database. Almost everything in Notion is a block, and blocks have comments and other stuff attached. If a block lived on one database and its comments on another, deleting the block could work while the comment update failed. So a block and everything attached to it live together, grouped by workspace, since people almost always work inside one workspace at a time.

They made 480 slices spread over 32 databases, 15 each. They picked 480 because it divides evenly by lots of numbers, so they can grow from 32 machines to 40 to 48. With 512 they'd have had to jump straight to 64.

Moving the data was its own project. The built-in copying couldn't keep up with how much they write, so they logged every change and replayed it onto the new databases. The first copy took about three days on a 96 CPU machine. Before switching, they read from old and new side by side and compared the results. One person wrote the migration and a different person wrote the checks, so the same bug couldn't sneak into both.

Looking back, they said they should have split earlier. And about one more week making the catch-up faster might have meant zero downtime.

RJRatish Jain
@ratishtwts · 17 Nov 2026

Was reading Netflix’s post on their write-ahead log service. The part about multi-partition writes stuck with me.

The problem:
Their KV stores can’t update rows across partitions atomically. If a write fails partway, some rows change and some don’t.
What they do instead:

Write every mutation to a separate durable KV table, each with a sequence number

After the last one, write a completion marker
Send a Kafka message saying the batch is ready
Consumer reads the full batch from the durable table
Checks the marker exists, then applies the rows in order
How failures play out:

Consumer crashes: batch is still in the durable table, so it gets replayed
Database is down: retry later, nothing is lost
Client dies mid-batch: no marker, so the partial batch is never applied

The detail I liked:
Kafka is only the trigger. The durable table is the source of truth for what was supposed to happen.
It’s the same idea as a database WAL on a single node, moved into a shared service so any team can use it.

We're still so small but I'm loving the team we've got at Superlogical. They're so talented and kind and love their craft. It's a different era of software development and our expectations and practices reflect that. I want to share a bit about how we work.

First, everyone is trusted to push to main. We do machine-aided code review pre-push and human plus more machine-aided code review post-push. Limited to no PRs.

Culturally, we've all agreed that if we ever hire someone who we DON'T trust to push directly to main, then they probably aren't the right fit for the team (so far, not an issue).

Some common sense here: if someone is stepping outside their lane or comfort zone, we'll open PRs. For example, I'm pretty trash at macOS/iOS UI, so I'll open PRs for UI-affecting functionality and ask for eyeballs/help. But for business logic and internals, I push to main.

Second, everyone can cut a release. Our release process is fully automated and when you start a release (for any platform) it triggers a Slack notification and a 15 minute countdown.

The 15 minute warning is a final gate that allows people to review plus collaborate on a changelog. During that 15 minutes, anyone in the company can pause the release rollout. After 15 minutes, the train leaves the station. You can't override the 15 minutes (except to pause). It gives everyone a chance to step in.

Third, we avoid synchronization through fast remediation rather than through planning. The server and clients on various platforms ship features as fast as they can. We use post-hoc human review and AI-assistance to identify feature mismatches across products ("Windows has support for X and Mac doesn't." or "Mac and Windows differ in their behaviors for Y in this way.").

This avoids expensive "sync" meetings and coordination. We trust that producers of features are mindful of what they're producing and we trust that adjacent product lines will self-synchronize quickly. In practice, we see feature parity across platforms within 24 to 48 hours.

All of this works on mutual trust. It ONLY works with mutual trust.

Everyone at all times has to trust that they've got each others back:

1. Push to main only works if you fix your mess, or if you don't, that someone else will quickly but that you'd do the same (and generally in equal amounts).

2. Anyone can deploy only works if you trust everyone to cut at the right time, with the right changelog, and that people will respect the 15 minute timer.

3. Sync through fast remediation only works if you trust other teams will pick up and integrate your work quickly, which only works if you would too. It also only works if you are fairly producing mismatches (e.g. not constantly).

We've got a great team. I know we're still small and that these practices will change in many ways as we scale. But this is already a markedly different practice than what I would've done 15 years ago.

In general, we are building from day 1 on a foundation of mutual respect, excellence, and trust. And it's been awesome.

- It's sort of like everyone who thinks they want TDD really wants code that is written so it could be tested (or at least could be very simply modified to be tested, such as by taking a function as an argument to modify behavior at test time)

- to what i have experienced is that one type of microservices is a distributed system, where a bunch of microservices coordinate to perform some business process. This is obviously easier to do in a monolith, since you get things like transactions and shared data models. With microservices, you have to adopt complex patterns like the Saga Pattern to coordinate microservices, and use patterns like CQRS to synchronized data between microservices. I personally would avoid going down the microservices path in this situation unless a really good reason presented itself.

- Another type of microservices is just a group of completely separate programs. There is a temptation to add features to existing monoliths because you don't have to create another repo, another CI/CD pipeline, etc. But then you have a monolith that is a bunch of random services cobbled together because of convenience, not because it makes sense for them to belong together. So, you have to deploy unrelated features for a change to one service. In this context, I don't see what's wrong with creating a new microservice at the beginning, or pinching out a microservice out of an existing monolith.

Not every AI application needs an AI agent.

Sometimes one LLM call is enough. Sometimes a predefined workflow is better.

Anthropic describes 5 patterns for building effective AI systems.

Here they are, with practical examples. 🧵

1. Prompt Chaining

Break a large task into smaller steps.

The output of one LLM call becomes the input of the next.

Example: Generate an article outline → review it → write the article → check the final result.

Use this when the steps are predictable.

2. Routing

Classify an incoming request and send it to the right handler.

Example:
Refund request → Refund handler.
Technical issue → Support handler.
General question → FAQ handler.

Think of it as an API router, but for AI tasks.

3. Parallelization

Run multiple LLM calls at the same time and combine their results.

Two approaches:

Sectioning: Split a task into independent subtasks.
Voting: Run the same task multiple times and compare the results.

Example: Review code for security, performance, and maintainability in parallel.

4. Orchestrator-Workers

An orchestrator (a central LLM) breaks a task into smaller tasks and delegates them to worker LLMs.

Example: An AI coding assistant identifies which files need changes, delegates the work, and combines the results.

Unlike basic parallelization, the subtasks are decided dynamically.

5. Evaluator-Optimizer

One LLM generates an output. Another evaluates it and provides feedback.

The generator uses that feedback to improve the result.

Example: Generate a SQL query → review correctness and performance → improve the query → repeat.

Useful when you have clear criteria to evaluate the output.

6. When do you actually need an AI agent?

Use an agent when you cannot predict all the steps in advance.

The LLM decides what to do, selects tools, observes the results, and chooses its next action.

Example: A coding agent inspects a repository, modifies files, runs tests, investigates failures, and tries again.

7. One more lesson: Design your tools well.

Anthropic calls this the Agent-Computer Interface (ACI).

It means designing tools so an AI model can understand and use them reliably.

Clear tool names, descriptions, parameters, and examples matter.

Sometimes improving a tool is more effective than improving the prompt.

The biggest takeaway:

Don't build an agent just because you can.

Start with the simplest architecture that solves the problem.

Add complexity only when it improves the outcome.
