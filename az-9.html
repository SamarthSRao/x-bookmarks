"Effective Go" is the most powerful FREE resource on the internet to study Go. But it's too long. So I trimmed down the most important concepts:

1. Name things the Go way
- Package names should be short, lowercase, and simple.

Use:
> bufio.Reader
> ring.New
> io.Reader

Not:
> bufio.BufReader
> ring.NewRing
> io.IReader

The package name is already part of the API.

2. Keep control flow flat
- In Go, readable code usually means early returns.
- Avoid deeply nested if/else chains.
- Handle the error. Return early.

3. Use multiple return values properly
- Go doesn't hide failures behind exceptions.
- Return both the value and the error.

Example:
> value, err := doSomething()
> if err != nil {
> return err
> }
> return value, nil

4. Use defer for cleanup
- Open a file? Defer the close.
- Lock a mutex? Defer the unlock.
- Acquire a resource? Defer the release.
- defer keeps cleanup close to setup, making code easier to maintain and harder to break.

5. Understand slices
- Slices are not arrays.
- They are lightweight descriptors that point to an underlying array.
- This means appending, passing, or modifying slices can affect the same underlying data.

Always write:
> s = append(s, x)

Not:
> append(s, x)

Because append can return a new slice header.

6. Design around useful zero values
- Good Go types should work even when they are not explicitly initialized.
- The zero value should be useful whenever possible.

Examples:
> bytes.Buffer
> sync.Mutex
> empty slices
> zero-value structs

- This makes APIs simpler and reduces unnecessary constructors.

7. Keep interfaces small
- In Go, interfaces are usually tiny.
- Don't create large interfaces too early.
- Define behavior with the smallest possible method set.

Examples:
> io.Reader
> io.Writer
> fmt.Stringer
> http.Handler

- Accept interfaces. Return concrete types.

8. Don't panic for normal errors
- "panic" is not for regular failures.
- Use panic only when the program reaches a truly unrecoverable state.
- For normal errors, return an error.

Bad:
> panic("file not found")

Good:
> return fmt.Errorf("open config: %w", err)

Let the caller decide how to handle the failure.

9. Share memory by communicating
- Go's concurrency model is built around goroutines and channels.
- Don't communicate by manually sharing memory everywhere.
- Use channels when ownership and coordination matter.
- But don't spawn goroutines blindly.
- Every goroutine should have a clear purpose.
- Every channel should have a clear owner.

10. Use gofmt. Always.
- Don't waste time arguing about formatting.
- Don't manually align code.
- Don't debate tabs vs spaces.
- Don't create your own formatting style.

Go already solved this.

Run:
> gofmt

And move on.

I was thinking to write a big post about my tech journey from the very beginning, from an intern at a small company to a SDE at FAANG company, I had received a lot of requests to share it so finally thought to share it today, so here we go:

1. So, giving a background, I graduated from a TIER-1 college but despite of that, I was never good at coding or didn't take much interest during my college days, because of that I was only able to crack an intern + ppo opportunity after the end of my college.

2. Unfortunately, after the internship, I didn't get the PPO, reason was my performance was decent, I tried to give my best but couldn't make it to a full time role.

3. Tbh, I was so hopeless and cried that day and I was not able to get any interview calls or offers for next 4-5 months, I was kind of little depressed.

4. I was at a stage where I was ready to work for any company and for any pay, because I wanted a job, wanted experience, wanted to come out of this unemployed ere.

5. Then luckily, after 5 months of intern and 9 months of graduation, I got my 1st ever full time job at IBM, tbh I was not happy with the role and pay I got but I was so so happy because I just wanted to work and wanted to go outside and explore.

6. For few months, I was so happy, went to Blr, met people, explore places, life was good, but then I realised, I shouldn't be settle for this, I know my potential and I can do a lot better.

7. Working in a big FAANG company like Google, Amazon, Microsoft was always my dream and this time now I was serious and decided I will do it, no matter what.

8. I started doing DSA seriously for 7-8 months, at least 1-2 problems a day, parallely, I started learning Dev and made many projects, plus learnt few of the basics concepts of Low Level Design.

9. After building this consistency and preparation, I was feeling a little confident and ready to apply.

10. Though it looks easy but applying and getting responses was always a tough part.

11. Luckily, one day, I got shortlist for Amazon interview rounds after clearing their OA and the process went for a month and luckily, by God's grace, I achieved my dream to work in FAANG and I couldn't tell how happy I was that day, best day of my life, I worked at IBM for around 1.2 years and then joined Amazon.

Below are the few points that can help aspiring candidates in their journey:

1. Pick one language (C++/Java/Python)
Stop hopping. Go deep.

2. Master DSA basics
Arrays → Strings → Recursion → Trees → Graphs
Focus on understanding, not just solving.

3. Practice consistently
2–3 problems daily > 20 problems once a week

4. Build projects
Even simple ones. They show you can apply knowledge.

5. Learn from rejections
You’ll fail interviews. That’s part of the process.

6. Stay patient
FAANG prep is a 6–18 month journey, not a sprint.
Most people quit early. If you don’t, you’re already ahead.

At the end, all it matters is your consistency, hardwork, patience and belif in yourself.

--- Go Learning Tips ---

> Focus on understanding when to use mutexes, channels, interfaces, generics, and reflection—build projects that heavily incorporate these
> Build applications that leverage Go's concurrency model, especially those that would require external infrastructure in other languages
> Dedicate time to mastering concurrency patterns
> Skip frameworks initially to grasp how things work under the hood
> Ship small projects to appreciate Go's simplicity combined with concurrency
> Write testable code by passing dependencies into constructors to avoid circular dependency issues; consider DI tools like fx but recognize they're not always necessary
> Learn the appropriate use cases for Cobra versus standard flags

Not every AI application needs an AI agent.

Sometimes one LLM call is enough. Sometimes a predefined workflow is better.

Anthropic describes 5 patterns for building effective AI systems.

Here they are, with practical examples. 🧵

1. Prompt Chaining

Break a large task into smaller steps.

The output of one LLM call becomes the input of the next.

Example: Generate an article outline → review it → write the article → check the final result.

Use this when the steps are predictable.

2. Routing

Classify an incoming request and send it to the right handler.

Example:
Refund request → Refund handler.
Technical issue → Support handler.
General question → FAQ handler.

Think of it as an API router, but for AI tasks.

3. Parallelization

Run multiple LLM calls at the same time and combine their results.

Two approaches:

Sectioning: Split a task into independent subtasks.
Voting: Run the same task multiple times and compare the results.

Example: Review code for security, performance, and maintainability in parallel.

4. Orchestrator-Workers

An orchestrator (a central LLM) breaks a task into smaller tasks and delegates them to worker LLMs.

Example: An AI coding assistant identifies which files need changes, delegates the work, and combines the results.

Unlike basic parallelization, the subtasks are decided dynamically.

5. Evaluator-Optimizer

One LLM generates an output. Another evaluates it and provides feedback.

The generator uses that feedback to improve the result.

Example: Generate a SQL query → review correctness and performance → improve the query → repeat.

Useful when you have clear criteria to evaluate the output.

6. When do you actually need an AI agent?

Use an agent when you cannot predict all the steps in advance.

The LLM decides what to do, selects tools, observes the results, and chooses its next action.

Example: A coding agent inspects a repository, modifies files, runs tests, investigates failures, and tries again.

7. One more lesson: Design your tools well.

Anthropic calls this the Agent-Computer Interface (ACI).

It means designing tools so an AI model can understand and use them reliably.

Clear tool names, descriptions, parameters, and examples matter.

Sometimes improving a tool is more effective than improving the prompt.

The biggest takeaway:

Don't build an agent just because you can.

Start with the simplest architecture that solves the problem.

Add complexity only when it improves the outcome.

anthropic.com/engineering/building-effective-agents
