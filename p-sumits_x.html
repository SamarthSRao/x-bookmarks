One of the most important and commonly asked JavaScript interview questions is:

“Can you explain prototypal inheritance?”

If you are asked this question cover these points 👇

1. What is Prototypal Inheritance?

JavaScript allows objects to inherit properties and methods directly from other objects via a chain of prototypes
- this is called prototypal inheritance.

2. What is __proto__?

Every object has an internal property called __proto__ (or [[Prototype]]), which points to the object it inherits from.

const animal = { eats: true };
const rabbit = Object.create(animal);
console.log(rabbit.__proto__ === animal); // true

3. What is .prototype?

.prototype is a property of constructor functions only.

It’s used to define shared methods for all instances created using the constructor.

function Animal() {}
Animal.prototype.walk = function() { console.log("walking"); };

const dog = new Animal();
dog.walk(); // "walking"

5. Prototype Chain

When you access a property:
JS first looks at the object
Then its __proto__
And keeps climbing up until it finds the property or reaches null.

rabbit -> animal -> Object.prototype -> null

6. How It Looks in the Browser Console

const animal = { eats: true };
const rabbit = Object.create(animal);
rabbit.jumps = true;
console.log(rabbit);

Expanding in DevTools shows:

{
jumps: true
[[Prototype]]: {
eats: true
[[Prototype]]: Object
}
}

__proto__ is a developer-accessible alias for the internal [[Prototype]] property.

7. Modern Approach – ES6 Classes

ES6 classes are just syntactic sugar over JavaScript’s prototypal inheritance system
Classes use prototypal inheritance under the hood.

class Animal {
eat() { console.log("eats"); }
}

const cat = new Animal();
cat.eat(); // "eats"

8. Benefits

Memory efficient (methods shared across instances)
Dynamic: you can modify prototype at runtime

9. Drawbacks

Debugging prototype chains can be tricky
Confusing for those coming from classical OOP backgrounds

API concepts that are discussed in interviews , don't skip these if you are a backend dev :

1. Idempotency: Know why PUT/DELETE are idempotent but POST isn’t. Helps avoid accidental double writes.

2. Pagination: Offset works until scale hits. Cursor/keyset is what you need for big data sets.

3. Versioning: URI vs Header vs Query param. There’s no one right way, just tradeoffs.

4. Rate limiting: Token bucket > naive fixed window if you care about fairness.

5. Error contracts: 400 (bad request) ≠ 422 (validation issue) ≠ 409 (conflict). Don’t just throw 500 everywhere.

6. Caching: ETag + Cache-Control save you from unnecessary DB load.

7. Security: JWTs expire for a reason. Don’t stuff user PII inside them.

8. N+1 Queries: Kill them early. Use batching or joins when returning nested resources.

9. Docs: OpenAPI/Swagger is not optional.

10. Consistency: Sometimes cached data is good enough.
